标题: SEP 指南  
描述: 规范增强提案(SEP)指南，用于提出对模型上下文协议的修改建议  

## 什么是SEP？  

SEP代表规范增强提案(Specification Enhancement Proposal)。SEP是一份设计文档，旨在向MCP社区提供信息，或描述模型上下文协议及其流程或环境的新功能。SEP应简明扼要地提供功能的技术规范及其设计理由。  

我们期望SEP成为以下事项的主要机制：提出重大新功能、收集社区对某个问题的意见、记录已纳入MCP的设计决策。SEP作者有责任在社区内建立共识并记录不同意见。  

由于SEP以版本控制仓库(GitHub Issues)中的文本文件形式维护，其修订历史就是功能提案的历史记录。  

## 什么情况下需要提交SEP？  

SEP流程旨在用于那些足够重大的变更，这些变更需要广泛的社区讨论、正式的设计文档以及决策过程的历史记录。对于较小或更直接的变更，通常使用普通的GitHub问题或拉取请求更为合适。  

如果您的变更涉及以下任何一项，请考虑提交SEP：  

- **新功能或协议变更**：任何添加、修改或删除模型上下文协议功能的变更。包括：  
  - 新增API端点或方法  
  - 修改现有数据结构或消息的语法或语义  
  - 引入新的标准以实现不同MCP兼容工具之间的互操作性  
  - 对规范本身的定义、呈现或验证方式的重大变更  
- **破坏性变更**：任何不向后兼容的变更  
- **治理或流程变更**：任何改变项目决策机制或贡献指南(如本文档本身)的提案  
- **复杂或有争议的主题**：如果某项变更可能有多种有效解决方案或引发重大争议，SEP流程提供了必要的框架来探索替代方案、记录设计理由并在实施前建立社区共识  

## SEP类型  

SEP分为三类：  

1. **标准追踪类(Standards Track)** SEP描述模型上下文协议的新功能或实现。也可描述将在核心协议规范之外支持的互操作性标准。  
2. **信息类(Informational)** SEP描述MCP设计问题，或向MCP社区提供一般性指南或信息，但不提议新功能。信息类SEP不一定代表MCP社区的共识或建议。  
3. **流程类(Process)** SEP描述围绕MCP的流程，或提议对流程的变更(或流程中的事件)。流程类SEP类似于标准追踪类SEP，但适用于MCP协议本身之外的领域。  

## 如何提交SEP  

SEP流程始于对模型上下文协议的新想法。强烈建议单个SEP仅包含一个关键提案或新想法。小的增强或补丁通常不需要SEP，可以通过向MCP仓库提交拉取请求直接进入开发流程。SEP越专注，往往越容易成功。  

每个SEP必须有一位**SEP作者**——负责按照下文描述的格式撰写SEP、在适当论坛引导讨论、并努力围绕该想法建立社区共识的人。SEP作者应首先确认该想法是否适合通过SEP提出。在MCP社区论坛(Discord、GitHub Discussions)发帖是进行确认的最佳方式。
### SEP 工作流程  

SEP 应以 GitHub Issue 的形式提交至[规范仓库](https://github.com/modelcontextprotocol/modelcontextprotocol)。标准 SEP 工作流程如下：  

1. **提交提案**：你作为 SEP 作者，创建一个[格式规范](#sep-format)的 GitHub Issue，并添加 `SEP` 和 `proposal` 标签。SEP 编号与 GitHub Issue 编号相同，二者可互换使用。  
2. **寻找赞助者**：找到一位核心维护者（Core Maintainer）或维护者（Maintainer）赞助你的提案。核心维护者和维护者会定期审查开放的提案列表，决定是否赞助。你可以在提案中提及[维护者列表](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/MAINTAINERS.md)中的相关人员。  
3. **分配赞助者**：找到赞助者后，GitHub Issue 将分配给该赞助者。赞助者会添加 `draft` 标签，确保标题中包含 SEP 编号，并分配里程碑。  
4. **非正式评审**：赞助者会对提案进行初步评审，并根据社区反馈可能要求修改。当提案准备好进入正式评审时，赞助者会添加 `in-review` 标签。  
5. **正式评审**：添加 `in-review` 标签后，SEP 将进入核心维护者团队的正式评审阶段。SEP 可能被接受、拒绝或退回修改。  
6. **休眠处理**：如果 SEP 在三个月内未找到赞助者，核心维护者可能会将其标记为 `dormant` 并关闭。  

---

### SEP 格式  

每个 SEP 应包含以下部分：  

1. **前言**——简短的描述性标题、作者姓名及联系方式、当前状态。  
2. **摘要**——简要（约 200 字）说明所解决的技术问题。  
3. **动机**——清晰阐述现有协议规范为何不足以解决 SEP 所针对的问题。对于希望修改 Model Context Protocol 的 SEP，动机部分至关重要。缺乏充分动机的 SEP 可能会被直接拒绝。  
4. **规范**——技术规范应描述新协议特性的语法和语义。规范需足够详细，以确保可互操作的竞争性实现。同时应提供包含规范修改的 PR。  
5. **理由**——解释设计决策的原因，包括考虑过的替代方案及相关工作。理由部分应体现社区共识，并讨论讨论过程中提出的重要反对意见或担忧。  
6. **向后兼容性**——所有引入向后不兼容性的 SEP 必须包含一节说明这些不兼容性及其严重程度，并解释作者计划如何处理。  
7. **参考实现**——参考实现必须在 SEP 进入 "Final" 状态前完成，但不必在 SEP 被接受前完成。尽管在编写代码前就规范和理由达成共识有其价值，但“粗略共识和运行代码”原则在解决协议细节讨论时仍非常有用。  
8. **安全影响**——如果 SEP 涉及安全问题，需明确写出，以确保评审者知晓。

### SEP 状态  

SEP 可能处于以下状态之一：  

- `proposal`：未找到赞助者的 SEP 提案。  
- `draft`：已找到赞助者的 SEP 提案。  
- `in-review`：准备进入评审的 SEP 提案。  
- `accepted`：SEP 已被核心维护者接受，但仍需最终措辞和参考实现。  
- `rejected`：SEP 被核心维护者拒绝。  
- `withdrawn`：SEP 被撤回。  
- `final`：SEP 已完成定稿。  
- `superseded`：SEP 已被更新的 SEP 取代。  
- `dormant`：未找到赞助者并被关闭的 SEP。
### SEP审核与决议

SEP提案由MCP核心维护团队每两周进行一次审核。

SEP提案若要被采纳，需满足以下基本条件：

- 提供展示提案可行性的原型实现
- 对MCP生态系统具有明确价值
- 获得社区支持并达成共识

SEP提案通过后，必须完成其参考实现。当参考实现完成并合并至主代码库时，提案状态将变更为"最终版"。

SEP提案也可能被"拒绝"或"撤回"。被"撤回"的提案未来可以重新提交。

## 报告SEP缺陷或提交更新

报告缺陷或提交更新的方式取决于多种因素，包括SEP的成熟度、作者偏好以及反馈性质。对于尚未进入`最终`状态的SEP，建议直接将意见和修改发送给原作者。SEP定稿后，可通过GitHub的issue评论或参考实现的pull request提交修正。

## SEP所有权转移

有时需要将SEP所有权转移给新作者。原则上我们建议保留原始作者作为共同作者，但这最终由原始作者决定。合理的转移理由包括：原始作者无暇继续维护、失去兴趣或失联（如邮件无响应）。不合理的转移理由则包括单纯不认同SEP方向。我们鼓励围绕SEP建立共识，若无法达成，您始终可以提交竞争性提案。
