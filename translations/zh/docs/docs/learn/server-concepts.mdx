---
title: 服务器核心概念
description: "理解MCP服务器的核心概念"
---

MCP服务器是通过标准化协议接口向AI应用提供特定功能的程序。每个服务器专注于特定领域的功能实现。

典型实例包括：文档管理的文件系统服务器、消息处理的邮件服务器、行程规划的旅行服务器，以及数据查询的数据库服务器。每个服务器都为AI应用带来领域专属的能力。

## 核心构建模块

服务器通过三大构建模块提供功能：

| 构建模块      | 用途                     | 控制方               | 现实案例                                                   |
| ------------- | ------------------------ | -------------------- | ---------------------------------------------------------- |
| **工具**      | AI执行动作               | 模型控制             | 查询航班、发送消息、创建日历事件                           |
| **资源**      | 上下文数据               | 应用控制             | 文档、日历、邮件、天气数据                                 |
| **提示模板**  | 交互模板                 | 用户控制             | "规划假期"、"汇总我的会议"、"起草邮件"                    |

### 工具 - AI动作执行

工具使AI模型能够通过服务器实现的函数执行操作。每个工具定义具有类型化输入输出的特定操作，模型根据上下文请求工具执行。

#### 概览

工具是LLM可调用的模式化接口，MCP使用JSON Schema进行验证。每个工具执行单一操作，具有明确定义的输入输出。最关键的是，工具执行需要用户明确授权，确保用户始终掌控模型执行的动作。

**协议操作：**

| 方法          | 用途                     | 返回内容                             |
| ------------- | ------------------------ | ------------------------------------ |
| `tools/list`  | 发现可用工具             | 包含模式定义的工具数组               |
| `tools/call`  | 执行特定工具             | 工具执行结果                         |

**工具定义示例：**

```typescript
{
  name: "searchFlights",
  description: "查询可用航班",
  inputSchema: {
    type: "object",
    properties: {
      origin: { type: "string", description: "出发城市" },
      destination: { type: "string", description: "到达城市" },
      date: { type: "string", format: "date", description: "旅行日期" }
    },
    required: ["origin", "destination", "date"]
  }
}
```

#### 示例：执行动作

工具使AI应用能代用户执行操作。在旅行规划场景中，AI应用可能使用多个工具协助预订行程。

首先通过

```
searchFlights(origin: "纽约", destination: "巴塞罗那", date: "2024-06-15")
```

查询航班，`searchFlights`会向多家航空公司查询并返回结构化航班选项。选定航班后，通过

```
createCalendarEvent(title: "巴塞罗那之旅", startDate: "2024-06-15", endDate: "2024-06-22")
```

创建日历事件标记旅行日期。最后通过

```
sendEmail(to: "team@work.com", subject: "休假通知", body: "...")
```

发送休假邮件通知同事。

每个工具执行都需要用户明确授权，确保完全掌控AI执行的所有操作。
#### 用户交互模型

工具由模型控制，意味着AI模型能自动发现并调用它们。但MCP通过多种机制强调人为监督。应用程序应在界面中清晰展示可用工具，并在工具被考虑或使用时提供视觉提示。任何工具执行前，必须向用户显示明确的审批对话框，准确说明该工具将执行的操作。

出于信任与安全考虑，应用程序通常要求手动审批，赋予用户拒绝工具调用的权利。典型实现方式包括审批对话框、预审批特定安全操作的权限设置，以及记录所有工具执行结果的活动日志。

### 资源 - 上下文数据

资源提供了结构化访问信息的途径，宿主应用程序可获取这些信息并将其作为上下文提供给AI模型。

#### 概述

资源暴露来自文件、API、数据库或其他任何AI需要理解上下文的数据源。应用程序能直接访问这些信息，并决定使用方式——无论是选择相关片段、通过嵌入搜索，还是全部传递给模型。

资源采用基于URI的标识体系，每个资源拥有唯一URI（如`file:///path/to/document.md`）。它们声明MIME类型以进行恰当内容处理，并支持两种发现模式：具有固定URI的**直接资源**，以及带有参数化URI的**资源模板**。

**资源模板**通过URI模板实现动态资源访问。例如`travel://activities/{city}/{category}`模板可通过替换`{city}`和`{category}`参数来获取筛选后的活动数据。如`travel://activities/barcelona/museums`将返回巴塞罗那所有博物馆信息。资源模板包含标题、描述和预期MIME类型等元数据，使其具备可发现性和自描述性。

**协议操作：**

| 方法                      | 用途                         | 返回内容                                |
| ------------------------- | ---------------------------- | --------------------------------------- |
| `resources/list`          | 列出可用直接资源             | 资源描述符数组                          |
| `resources/templates/list`| 发现资源模板                 | 资源模板定义数组                        |
| `resources/read`          | 获取资源内容                 | 带元数据的资源数据                      |
| `resources/subscribe`     | 监控资源变更                 | 订阅确认                                |
#### 示例：访问上下文数据  

继续以旅行计划为例，资源为AI应用提供了获取相关信息的能力：  

- **日历数据**（`calendar://events/2024`）——用于检查可用时间  
- **旅行证件**（`file:///Documents/Travel/passport.pdf`）——包含重要信息  
- **历史行程**（`trips://history/barcelona-2023`）——用户可选择沿用哪次旅行的风格  

资源无需手动复制数据，而是直接向AI应用提供原始信息。应用可自行决定如何处理这些数据，例如筛选部分数据（使用嵌入或关键词搜索），或直接将资源的原始数据传递给模型。在本例中，规划阶段AI应用可传递日历数据、天气数据和旅行偏好，以便模型检查可用时间、查询天气模式并参考用户偏好。  

**资源模板示例：**  

```json  
{  
  "uriTemplate": "weather://forecast/{city}/{date}",  
  "name": "weather-forecast",  
  "title": "天气预测",  
  "description": "获取任意城市和日期的天气预报",  
  "mimeType": "application/json"  
}  

{  
  "uriTemplate": "travel://flights/{origin}/{destination}",  
  "name": "flight-search",  
  "title": "航班搜索",  
  "description": "查询城市间的可用航班",  
  "mimeType": "application/json"  
}  
```  

这些模板支持灵活查询。天气数据可按城市/日期组合获取预测，航班可搜索任意两座机场间的航线。当用户输入“NYC”作为`origin`机场并开始输入“Bar”作为`destination`时，系统可建议“巴塞罗那（BCN）”或“巴巴多斯（BGI）”。  

#### 参数补全  

动态资源支持参数补全。例如：  
- 在`weather://forecast/{city}`中输入“Par”时，可能建议“巴黎”或“帕克城”  
- 系统帮助发现有效值，无需用户掌握精确格式  

#### 用户交互模型  

资源由应用驱动，主机可灵活选择获取、处理和呈现上下文的方式。常见交互模式包括：  
- 树形或列表视图：以类似文件夹的结构浏览资源  
- 搜索和筛选界面：查找特定资源  
- 基于启发式或AI选择的自动上下文包含  
- 手动选择界面  

应用可自由采用适合其需求的资源发现界面。协议不强制特定UI模式，支持以下方式：  
- 带预览功能的资源选择器  
- 基于当前对话上下文的智能建议  
- 批量选择以包含多个资源  
- 与现有文件浏览器或数据资源管理器集成  

### 提示——交互模板  

提示提供可复用的模板，允许MCP服务器作者为特定领域提供参数化提示，或展示如何最佳使用MCP服务器。  

#### 概述  

提示是结构化模板，定义了预期输入和交互模式。它们由用户控制，需显式调用而非自动触发。提示可感知上下文，引用可用资源和工具以创建完整工作流。与资源类似，提示支持参数补全，帮助用户发现有效参数值。  

**协议操作：**  

| 方法           | 用途                     | 返回内容                          |  
| -------------- | ------------------------ | --------------------------------- |  
| `prompts/list` | 发现可用提示             | 提示描述符数组                    |  
| `prompts/get`  | 获取提示详情             | 包含参数的完整提示定义            |
#### 示例：高效工作流

提示为常见任务提供结构化模板。以旅行规划场景为例：

**"规划假期"提示模板：**

```json
{
  "name": "plan-vacation",
  "title": "规划假期",
  "description": "引导完成假期规划流程",
  "arguments": [
    { "name": "destination", "type": "string", "required": true },
    { "name": "duration", "type": "number", "description": "天数" },
    { "name": "budget", "type": "number", "required": false },
    { "name": "interests", "type": "array", "items": { "type": "string" } }
  ]
}
```

相较于非结构化的自然语言输入，提示系统实现了：
1. 选择"规划假期"模板
2. 结构化输入：巴塞罗那、7天、3000美元、["海滩","建筑","美食"]
3. 基于模板的标准化流程执行

#### 用户交互模式

提示功能需用户主动调用，常见实现方式包括：斜杠命令（输入"/"查看可用提示如/plan-vacation）、可搜索的命令面板、高频提示专用按钮、以及智能推荐相关提示的上下文菜单。

该协议赋予开发者设计自由，核心原则包括：提示易发现性、功能描述清晰化、带验证的参数输入、模板底层逻辑透明化。

## 系统协同原理

当多个服务器通过统一接口协同工作时，MCP的真正威力才得以显现。

### 示例：多服务器旅行规划

假设某AI应用连接三个服务器：
1. **旅行服务器** - 处理航班、酒店及行程
2. **天气服务器** - 提供气候数据与预报
3. **日历/邮件服务器** - 管理日程与通讯

#### 完整工作流

1. **用户调用带参数的提示：**

   ```json
   {
     "prompt": "plan-vacation",
     "arguments": {
       "destination": "巴塞罗那",
       "departure_date": "2024-06-15",
       "return_date": "2024-06-22",
       "budget": 3000,
       "travelers": 2
     }
   }
   ```

2. **用户选择关联资源：**
   - `calendar://my-calendar/June-2024`（来自日历服务器）
   - `travel://preferences/europe`（来自旅行服务器）
   - `travel://past-trips/Spain-2023`（来自旅行服务器）

3. **AI处理请求：**

   AI首先读取所有选定资源获取上下文：从日历确认可用日期，从旅行偏好获取常用航司和酒店类型，从历史行程发现曾到访地点，从天气数据核查旅行期间气候条件。

   基于这些信息，AI会请求用户批准执行系列联动操作：查询纽约至巴塞罗那航班、筛选预算内酒店、创建行程日历事件、发送含详细安排的确认邮件。
