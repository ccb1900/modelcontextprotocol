模型上下文协议（MCP）采用正式治理模式，确保决策透明与社区参与。本文档阐述项目组织架构与决策流程。

## 技术治理

MCP项目采用与Python、PyTorch等开源项目类似的层级结构：

- **贡献者**社区：提交问题、发起拉取请求并为项目作贡献
- **维护者**小组：负责驱动MCP项目中各组件（如SDK、文档等）发展
- **核心维护者**团队：监督贡献者与维护者，把握项目整体方向
- **首席核心维护者**（2名）：拥有最终决策权
- 维护者、核心维护者与首席核心维护者共同构成**MCP指导组**

所有维护者都应高度认同MCP的设计理念。技术治理成员资格以个人为单位（非企业），不设企业专属席位，确保决策始终符合协议本身与开源社区的最佳利益。

### 沟通渠道

技术治理通过全体**维护者**、**核心维护者**及**首席维护者**共用的[Discord服务器](/community/communication#discord)进行。各维护组可自选辅助沟通渠道，但所有决策及相关讨论必须记录并透明公开于Discord服务器。

### 维护者职责

维护者负责MCP项目中的独立子项目或技术工作组（如特定语言SDK或文档子目录）。维护者可自主制定决策规则，但遇重大事项可提交核心维护者裁决。具体职责包括：

- 与社区贡献者保持建设性互动
- 持续优化所辖项目模块
- 完善配套文档、路线图等周边内容
- 向核心层传递社区建议

维护者可适时提名新增成员。其任免由核心/首席核心维护者全权决定，无需说明理由。维护者拥有对应代码库的写入/管理权限。
### 核心维护者  

核心维护者需深入理解模型上下文协议（Model Context Protocol，MCP）及其规范。他们的职责包括：  

- 设计、评审并推动MCP规范的演进，以及MCP项目的其他部分，例如文档；  
- 为项目阐明连贯的长期愿景；  
- 公平、透明地调解和解决争议问题，尽可能达成共识，必要时果断决策；  
- 任命或移除维护者；  
- 以MCP的最佳利益为出发点，对项目进行管理。  

核心维护者作为一个群体，有权通过多数投票否决维护者的任何决定。核心维护者有权以他们认为合适的方式解决争议，并应公开说明其决策过程。核心小组需自行制定决策流程。  

核心维护者通常对所有MCP代码库拥有写入和管理权限，但应与外部贡献者使用相同的贡献机制（通常是拉取请求）。基于安全考虑可作例外处理。  

### 首席维护者（BDFL）  

MCP有两位首席维护者：Justin Spahr-Summers 和 David Soria Parra。首席维护者有权否决核心维护者或普通维护者的任何决定。这一模式在开源社区中通常被称为“终身仁慈独裁者”（Benevolent Dictator for Life，BDFL）。首席维护者应公开其决策过程，并给出清晰的决策理由。首席维护者属于核心维护者小组。  

首席维护者负责确认或移除核心维护者。  

在可行的情况下，首席维护者应担任MCP项目所有基础设施的管理员，包括但不限于所有沟通渠道、GitHub组织及代码库。  

### 决策流程  

核心维护者小组每两周举行一次会议，讨论并投票表决提案，同时讨论其他必要议题。必要时，可通过共享的Discord服务器讨论并投票表决较小的提案。  

首席维护者、核心维护者及普通维护者小组应尝试每三至六个月线下会面一次。  

## 流程  

核心及首席维护者负责模型上下文协议的所有方面，包括文档、议题、内容建议以及[MCP项目](https://github.com/modelcontextprotocol)下的其他部分。普通维护者负责其所属MCP项目领域的文档、议题及内容建议，但也鼓励参与MCP项目的整体维护工作。维护者、核心维护者及首席维护者应与外部贡献者使用相同的贡献流程，而非直接修改代码库。这有助于明确意图并促进讨论。  

### 项目与工作组  

MCP项目分为两大结构：项目和工作组。  

项目是维护在独立代码库中的具体组件，包括规范、TypeScript SDK、Go SDK、检查器及其他实现产物。  

工作组是协作论坛，供感兴趣的各方讨论MCP的特定方面，但不维护代码库。这些小组专注于传输协议、客户端实现等跨领域问题。
#### 治理原则

所有项目和工作组在遵循以下核心原则的前提下实行自治：

1. 明确的贡献与决策流程  
2. 开放的沟通与透明的决策  

二者均须做到：
- 记录其贡献流程  
- 保持沟通透明化  
- 公开决策（工作组必须发布会议记录和提案）  

未指定流程的项目和工作组默认采用：
- GitHub 的拉取请求和议题作为贡献渠道  
- 官方 [MCP贡献者Discord](/community/communication#discord) 中的公共频道  

#### 维护职责

无专属维护者的组件（如文档）由核心维护者负责。这些组件通过拉取请求遵循标准贡献指南，维护者负责审核，重大变更需提交核心维护者复审。

鼓励核心维护者和维护者改进MCP项目的任何部分，无论是否属于其正式维护范围。

### 规范项目

#### 规范增强提案（SEP）

对规范的修改提案必须以书面形式提交，开头需包含提案摘要，阐明待解决的**问题**、提出的**解决方案**、**替代方案**、**考量因素**、**预期结果**及**风险**。[SEP指南](/community/sep-guidelines)详述了提案的标准结构。SEP应作为议题提交至[规范仓库](https://github.com/modelcontextprotocol/specification)并标记`proposal, sep`标签。

所有提案必须获得MCP指导组（维护者、核心维护者或首席核心维护者）中一名**发起人**的支持。发起人负责确保提案积极开发、符合质量标准，并负责在核心维护者会议上陈述讨论。维护者与核心维护者组应定期审查未获发起人的公开提案。六个月内未找到发起人的提案将自动驳回。

提案获得发起人后，将被分配给该发起人并标记为`draft`状态。

## 沟通机制

### 核心维护者会议

核心维护者组每两周召开会议讨论提案与项目进展。提案相关记录应公开。核心维护者组每3-6个月应争取举行线下会议。

### 公共交流

MCP项目在[官方Discord服务器](/community/communication#discord)为各兴趣组设立开放聊天室。特定沟通可能使用私有频道。

## 维护者提名、确认与移除

### 基本原则

- 模块维护者组的成员资格基于**个人**能力授予，需通过贡献、评审和讨论展现领域专业能力，并与MCP整体方向一致  
- **维护者**组成员需持续展现与MCP原则的高度契合  
- 模块维护者与核心维护者无任期限制  
- 工作组或子项目维护者长期未活跃时可转为"荣誉"状态，各维护者组可自定义适用其领域的判定周期  
- 成员资格归属个人而非企业  

### 提名与移除

- 核心维护者负责维护者的增补与移除，需考虑现有维护者意见  
- 首席维护者负责核心维护者的增补与移除
