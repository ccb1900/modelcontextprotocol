在模型上下文协议(MCP)中，传输机制为客户端与服务端之间的通信提供了基础。传输层负责处理消息收发背后的底层机制。  

## 消息格式  

MCP采用[JSON-RPC](https://www.jsonrpc.org/) 2.0作为有线传输格式。传输层需要将MCP协议消息转换为JSON-RPC格式进行传输，并将接收到的JSON-RPC消息转换回MCP协议消息。  

主要使用三类JSON-RPC消息：  

### 请求  

```typescript  
{  
  jsonrpc: "2.0",  
  id: number | string,  
  method: string,  
  params?: object  
}  
```  

### 响应  

```typescript  
{  
  jsonrpc: "2.0",  
  id: number | string,  
  result?: object,  
  error?: {  
    code: number,  
    message: string,  
    data?: unknown  
  }  
}  
```  

### 通知  

```typescript  
{  
  jsonrpc: "2.0",  
  method: string,  
  params?: object  
}  
```

### 可流式HTTP  

可流式HTTP传输使用HTTP POST请求进行客户端到服务端的通信，并可选地通过服务器推送事件(SSE)实现服务端到客户端的通信。  

适用场景：  
- 开发基于Web的集成方案  
- 需要通过HTTP进行客户端服务端通信  
- 需要保持会话状态  
- 支持多客户端并发  
- 实现可恢复的连接  

#### 工作原理  

1. **客户端到服务端通信**：每个从客户端发出的JSON-RPC消息都作为新的HTTP POST请求发送到MCP端点  
2. **服务端响应**：服务端可选择两种响应方式：  
   - 返回单个JSON响应(`Content-Type: application/json`)  
   - 通过SSE流返回多条消息(`Content-Type: text/event-stream`)  
3. **服务端到客户端通信**：服务端可通过以下方式向客户端发送请求/通知：  
   - 由客户端请求触发的SSE流  
   - 通过HTTP GET请求到MCP端点建立的SSE流
#### 服务端

#### 会话管理

流式HTTP支持有状态会话以维持跨请求的上下文：

1. **会话初始化**：服务端可在初始化时通过`Mcp-Session-Id`头部分配会话ID
2. **会话保持**：客户端必须在后续请求中通过`Mcp-Session-Id`头部携带该ID
3. **会话终止**：可通过发送携带会话ID的HTTP DELETE请求显式终止会话

会话流程示例：

```typescript
// 服务端在初始化时分配会话ID
app.post("/mcp", (req, res) => {
  if (req.body.method === "initialize") {
    const sessionId = generateSecureId();
    res.setHeader("Mcp-Session-Id", sessionId);
    // 存储会话状态...
  }
  // 处理请求...
});

// 客户端在后续请求中携带会话ID
fetch("/mcp", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "Mcp-Session-Id": sessionId,
  },
  body: JSON.stringify(request),
});
```


#### 断线恢复与消息重传

为确保连接中断时的可靠性，流式HTTP提供：

1. **事件ID**：服务端可为SSE事件附加唯一ID用于追踪
2. **断点续传**：客户端可通过`Last-Event-ID`头部从最后接收的事件恢复
3. **消息重播**：服务端可从断连点重放遗漏消息

这些机制保障了网络不稳定时的可靠消息传递。
#### 安全注意事项  

在实现可流式 HTTP 传输时，请遵循以下安全最佳实践：  

1. **验证 Origin 头信息**：始终验证所有传入连接的 `Origin` 头信息，以防止 DNS 重绑定攻击。  
2. **绑定到本地主机**：在本地运行时，仅绑定到本地主机（127.0.0.1），而非所有网络接口（0.0.0.0）。  
3. **实施身份验证**：对所有连接使用适当的身份验证机制。  
4. **使用 HTTPS**：在生产环境中始终使用 TLS/HTTPS。  
5. **验证会话 ID**：确保会话 ID 具备加密安全性并正确验证。  

若未采取这些防护措施，攻击者可能通过 DNS 重绑定技术与本地 MCP 服务器进行远程交互。  

### 服务器发送事件（SSE）——已弃用  

<Note>  
  自协议版本 2024-11-05 起，SSE 作为独立传输方式已被弃用。  
  它已被可流式 HTTP 取代，后者将 SSE 作为可选的流式机制纳入其中。  
  如需向后兼容性信息，请参阅下方的[向后兼容性](#backwards-compatibility)部分。  
</Note>  

旧版 SSE 传输支持通过 HTTP POST 请求实现服务器到客户端的流式通信。  

过去在以下场景中使用：  

- 仅需服务器到客户端的单向流式传输  
- 受限制的网络环境  
- 实现简单的更新推送  

#### 旧版安全注意事项  

已弃用的 SSE 传输与可流式 HTTP 具有相似的安全注意事项，尤其是关于 DNS 重绑定攻击的部分。  
在使用可流式 HTTP 传输中的 SSE 流时，同样需要应用这些防护措施。

## 自定义传输协议

MCP 可轻松实现满足特定需求的自定义传输协议。任何传输实现只需符合 Transport 接口即可：

您可以为以下场景实现自定义传输协议：

- 自定义网络协议
- 专用通信通道
- 与现有系统集成
- 性能优化

<CodeGroup>

```typescript TypeScript
interface Transport {
  // 开始处理消息
  start(): Promise<void>;

  // 发送 JSON-RPC 消息
  send(message: JSONRPCMessage): Promise<void>;

  // 关闭连接
  close(): Promise<void>;

  // 回调函数
  onclose?: () => void;
  onerror?: (error: Error) => void;
  onmessage?: (message: JSONRPCMessage) => void;
}
```

```python Python
# 注意：虽然 MCP 服务通常使用 asyncio 实现，但我们建议
# 使用 `anyio` 实现传输协议等底层接口以获得更广泛的兼容性

@contextmanager
async def create_transport(
    read_stream: MemoryObjectReceiveStream[JSONRPCMessage | Exception],
    write_stream: MemoryObjectSendStream[JSONRPCMessage]
):
    """
    MCP 传输协议接口

    参数:
        read_stream: 读取传入消息的流
        write_stream: 写入传出消息的流
    """
    async with anyio.create_task_group() as tg:
        try:
            # 启动消息处理
            tg.start_soon(lambda: process_messages(read_stream))

            # 发送消息
            async with write_stream:
                yield write_stream

        except Exception as exc:
            # 错误处理
            raise exc
        finally:
            # 清理资源
            tg.cancel_scope.cancel()
            await write_stream.aclose()
            await read_stream.aclose()
```

</CodeGroup>

1. 连接错误
2. 消息解析错误
3. 协议错误
4. 网络超时
5. 资源清理

错误处理示例：

<CodeGroup>

```typescript TypeScript
class ExampleTransport implements Transport {
  async start() {
    try {
      // 连接逻辑
    } catch (error) {
      this.onerror?.(new Error(`连接失败: ${error}`));
      throw error;
    }
  }

  async send(message: JSONRPCMessage) {
    try {
      // 消息发送逻辑
    } catch (error) {
      this.onerror?.(new Error(`消息发送失败: ${error}`));
      throw error;
    }
  }
}
```

```python Python
# 注意：虽然 MCP 服务通常使用 asyncio 实现，但我们建议
# 使用 `anyio` 实现传输协议等底层接口以获得更广泛的兼容性

@contextmanager
async def example_transport(scope: Scope, receive: Receive, send: Send):
    try:
        # 创建双向通信流
        read_stream_writer, read_stream = anyio.create_memory_object_stream(0)
        write_stream, write_stream_reader = anyio.create_memory_object_stream(0)

        async def message_handler():
            try:
                async with read_stream_writer:
                    # 消息处理逻辑
                    pass
            except Exception as exc:
                logger.error(f"消息处理失败: {exc}")
                raise exc

        async with anyio.create_task_group() as tg:
            tg.start_soon(message_handler)
            try:
                # 返回通信流
                yield read_stream, write_stream
            except Exception as exc:
                logger.error(f"传输协议错误: {exc}")
                raise exc
            finally:
                tg.cancel_scope.cancel()
                await write_stream.aclose()
                await read_stream.aclose()
    except Exception as exc:
        logger.error(f"传输协议初始化失败: {exc}")
        raise exc
```

## 安全考量

实现传输协议时需注意：

### 认证与授权

- 部署可靠的认证机制
- 验证客户端凭证
- 采用安全的令牌处理方式
- 实施授权检查

### 数据安全

- 使用TLS加密网络传输
- 对敏感数据进行加密
- 验证消息完整性
- 设置消息大小限制
- 对输入数据进行净化处理

### 网络安全

- 实施速率限制
- 配置适当的超时设置
- 防范拒绝服务攻击
- 监控异常行为模式
- 配置正确的防火墙规则
- 对于基于HTTP的传输（包括Streamable HTTP），验证Origin头防止DNS重绑定攻击
- 本地服务器应仅绑定到localhost（127.0.0.1），而非所有接口（0.0.0.0）

## 向后兼容性

为保持不同协议版本间的兼容性：

### 服务端支持旧版客户端

希望支持使用已弃用HTTP+SSE传输的客户端的服务端应：

1. 同时提供旧版SSE、POST端点和新版MCP端点
2. 在两个端点上处理初始化请求
3. 为每种传输类型维护独立的处理逻辑

### 客户端支持旧版服务端

希望支持使用旧版传输的服务端的客户端应：

1. 接受可能使用任意传输类型的服务端URL
2. 尝试发送带有正确Accept头的InitializeRequest：
   - 若成功，则使用Streamable HTTP传输
   - 若返回4xx状态码，则回退到旧版SSE传输
3. 对于旧版服务端，发送GET请求并期待包含endpoint事件的SSE流

兼容性检测示例：

```typescript
async function detectTransport(serverUrl: string): Promise<TransportType> {
  try {
    // 首先尝试Streamable HTTP
    const response = await fetch(serverUrl, {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
        Accept: "application/json, text/event-stream",
      },
      body: JSON.stringify({
        jsonrpc: "2.0",
        method: "initialize",
        params: {
          /* ... */
        },
      }),
    });

    if (response.ok) {
      return "streamable-http";
    }
  } catch (error) {
    // 回退到旧版SSE
    const sseResponse = await fetch(serverUrl, {
      method: "GET",
      headers: { Accept: "text/event-stream" },
    });

    if (sseResponse.ok) {
      return "legacy-sse";
    }
  }

  throw new Error("不支持的传输协议");
}
```
